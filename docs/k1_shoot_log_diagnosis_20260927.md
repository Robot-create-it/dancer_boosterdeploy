## 最关键的代码缺陷：无球“保持”实际追随下沉

`tasks/locomotion/k1_shoot.py:54–59`：

```python
ball = self.controller.get_ball_position(self.cfg.ball_max_age)
if ball is None:
    LocomotionPolicy.compute_observation(self)
    self.reset()
    return self.robot.data.joint_pos.clone()
```

这是每 20 ms 重新读取当前角度并作为新目标，不是锁存丢球时的姿态。实机发布仍保留 Kp/Kd，速度目标和前馈力矩为零（`booster_robot_controller.py` 中 `create_low_cmd_publisher`、`ctrl_step`）。

按 PD 控制，位置项为 `Kp × (q_target - q_actual)`。每次采样时两者相等，位置项归零；采样间仍会产生误差，因而不能称为严格 Kp=0，但下一帧目标又追随实际下沉，无法积累抵抗重力所需的持久位置误差。行走时也没有平衡策略继续接管。

离线调用真实 `BaseController(K1ShootTaskCfg())`，先执行一次有球推理，再强制球输入为 None，改变左膝实测角：

| 实测左膝角（rad） | 返回目标角（rad） | 全身最大位置误差 | 左膝 Kp | 策略历史 |
|---|---|---|---|---|
| 0.3 | 0.3 | 0 | 100 | 被清空 |
| 0.4 | 0.4 | 0 | 100 | 被清空 |
| 0.5 | 0.5 | 0 | 100 | 被清空 |

这确认了支撑逻辑缺陷，而不是证明本次机器人当时执行了这些输入。

### 丢球分支比“超时 0.5 秒”更容易触发

- `booster_robot_controller.py::_vision_handler` 每收到一帧新的检测就重写球状态；该帧没有合格 Ball 时，立即写入 `valid=False`。
- `vision_ball.py::_select_object` 要求 Ball 置信度至少 60，位置有限且前向距离在 [-0.5, 15] 米内。画面有其他目标或低置信度球并不等于 shoot 有有效球。
- `get_ball_observation` 还要求图像、头部位姿和球都不过期，最大年龄 0.5 秒。

因此一帧漏检/低置信度就可能在下一个控制周期触发无球分支，**不是必须连续丢球 0.5 秒**。反复有球/无球还会清空历史和上一帧动作，重新启用 shoot 时缺乏连续性。

接近球时视野变化或遮挡可触发此路径，但本次没有保存 Ball 的逐帧分类、置信度、坐标和有效性，不能声称已经证实具体视觉诱因。

## 其他已发现问题及证据边界

1. **初始化重复切 Custom 后出现空命令。** 最新运行 17:23:57.060 报 expected 22, got 0。代码始终构造 22 个 MotorCmd，日志发生在底层 Reset Custom Command 之后，重置与命令到达的竞争是候选解释；不能据此认定 Python 一直发空数组，也不能用它直接解释几秒后的接近球异常。
2. **异常停止仍可能走默认 walking 退出。** `LocomotionPolicy.compute_observation` 在重力投影 z > -0.5（机身相对竖直倾斜超过约 60°）时调用 controller.stop；该路径设置 exit_event，却不把父进程的 `_safety_abort` 标为真。主循环随后仍可能请求 walking。离线输入约 63° 倾斜已验证策略停止；没有日志能证明本次是否触发此条件。直接切换内置步态后的保护阻尼已在两次运行确认。
3. **频率没有持续下降的文本证据。** 最新运行稳定窗口 Custom 调用 49.2608–50.1173 Hz、平均 49.8174 Hz；底层命令快照约 499.16 Hz。这是底层任务/快照计数，不等同于 ONNX 推理耗时，也不能排除单周期尖峰。
4. **未发现同期腿部掉线或电源急停证据。** 最新 Custom 窗口看到 17:23:56.948、17:24:01.698 两次头部 CAN 读失败；之前一次有多条头部读失败。最新退出前电量约 85.1%、电压 52.1–52.2 V，记录的急停标志为 0。头部通信异常值得继续查，但现有记录不能证明它导致球失效或全身软掉。
5. **视觉进程没有先崩溃。** 当前日志持续处理至 SIGINT；440 次检测中有两次零目标（#410、#411），其余总目标数不代表存在有效 Ball。检测时间戳间隔最大约 166.664 ms；没有逐帧绝对时间及控制状态对齐，不能把这两帧认定为软掉起点。

## 建议修复顺序

1. 优先修复无球支撑：禁止逐帧把实际下沉角刷新成保持目标。静态保持至少需要锁存目标；对行走/单脚支撑阶段，应设计并验证平稳过渡到零速平衡控制。单纯锁存姿态不保证动态稳定，不宜直接当作完整修复。
2. 给短暂视觉漏检加入明确的状态和过渡策略，记录丢球原因、持续时间、恢复事件；避免每次漏检都无条件清空策略历史。
3. 用可跨进程共享的停止原因区分人工退出、姿态保护和推理异常，核对退出接管策略；同时消除模式重复 reset 的命令空窗。
4. 下一次验证前落盘带时间戳的球有效性/置信度、图像与姿态年龄、IMU、q/dq、q_target、Kp/Kd、控制分支和退出原因。保留每次运行独立日志，才能闭合“输入失效 → 目标追随实测角 → 支撑变弱”的事故证据链。
