### 0 秒附近肩部力矩为什么异号

图中 0 秒仅表示两次试验的左髋都达到 -2.30 rad，并不是肩部或 policy 的共同起点。以下 `dq` 为关节角速度，`tau_est` 采用同一个 `/low_state` 串行关节的符号约定：

| 相对时间 | 试验 | 左肩 2：q / dq / tau_est | 右肩 6：q / dq / tau_est |
|---|---|---|---|
| -1.0 s | 固件 | +0.640 / -1.614 / -10.04 | +0.658 / -1.642 / -4.43 |
| -1.0 s | deploy | +0.610 / -0.255 / -14.00 | +0.624 / -0.190 / -12.75 |
| 0 s | 固件 | -1.528 / -2.164 / +11.94 | -1.385 / -1.231 / +14.00 |
| 0 s | deploy | +0.066 / +1.721 / -14.00 | +0.217 / +0.815 / -13.65 |
| +0.1 s | 固件 | -1.705 / -1.150 / +13.61 | -1.493 / -0.738 / +14.00 |
| +0.1 s | deploy | +0.084 / +0.003 / -14.00 | +0.224 / -0.033 / -13.44 |

在 -1 秒两边肩部 `tau_est` 同为负，不支持“整段曲线符号取反”的解释。接近 0 秒时，两边肩部角速度方向相反，力矩方向也相反；两边的力矩此时都与各自的角速度相反。固件肩部已快速到达负角度，正力矩表现为制动/抗负载；deploy 肩部仍在正角度附近，收到负方向目标，负力矩在关节几乎停止后仍保持。deploy +0.1 秒的左肩目标约 -0.181 rad、实测 +0.084 rad，`53 × (目标−实测) ≈ -14.0 N·m`，与反馈估计力矩一致。固件内部目标和手臂接触力未记录，无法进一步区分内部目标、速度阻尼和接触负载各自的贡献。

deploy 的发送角已经经过两次手臂限幅：策略内一次，发布 `/joint_ctrl` 前一次（`tasks/locomotion/k1_recovery.py`、`booster_deploy/controllers/booster_robot_controller.py`）。限幅规则是当前实测角 ± `effort_limit/kp`；关节 2/6 为 ±14/53 ≈ 0.264 rad，关节 5/9 为 ±14/55 ≈ 0.255 rad。在 15:36:29.5 左右，发布目标与实测差长期贴近这些界限。由此不能根据“小于 0.3 rad 的发送误差”推断原始 policy 参考也接近当前姿态；原始参考没有保存在这两份录制中。

录制时 `tasks/locomotion/k1_recovery.py` 的 `inference()` 在策略目标生成后调用过 `limit_arm_targets()`，`booster_deploy/controllers/booster_robot_controller.py` 的 `_publish_recovery_target()` 在发布前按最新反馈再调用一次，公式为 `q_send = clip(q_raw, q_measured - effort_limit/kp, q_measured + effort_limit/kp)`；手臂以外的关节不受这一步限制。后续删除这两处约束不能让 deploy 自动复现固件轨迹：固件 FDR 自身也有相同的手臂约束，且本次双臂在约 14 N·m 已持续停滞。更大的角度偏差可能只增加所请求的比例力矩及故障风险；原始策略参考、固件内部目标和两次接触状态仍未知。

## 力矩、堵转和供电

从左肘首次偏离初始位置 0.1 rad 的时刻开始，至故障前（固件取相同长度约 3 s），统计串行 `tau_est`。`|tau_est| ≥ 13.5 N·m` 且 `|dq| < 0.2 rad/s` 是本次分析的停滞判据，并非厂家故障阈值。

| 手臂关节 | 固件最长连续停滞 | deploy 最长连续停滞 |
|---|---:|---:|
| 2 左肩 | 0.022 s | 1.248 s（28.877～30.125） |
| 5 左肘 | 0 s | 1.228 s（28.897～30.125） |
| 6 右肩 | 0.032 s | 0.984 s（29.025～30.009） |
| 9 右肘 | 0 s | 1.282 s（28.843～30.125） |

deploy 在停滞时双肩、双肘的 `tau_est` 长期接近 ±14 N·m。约 15:36:29.035，左右髋的实测约 -2.329/-2.430、发送目标约 -2.901/-3.000，反馈估计力矩约 -54.8/-55.4 N·m；随后发生堵转。固件对应动作阶段手臂曾短时达到 14 N·m，但继续运动，没有持续高力矩静止。

图上右轴原有的 15 N·m 刻度容易被误读为固件输出达到 15 N·m。逐帧核对本次固件 FDR 动作，手臂关节 2～9 的最大 `|tau_est|` 为 14.0004 N·m；deploy 故障前最大值也为 14.0004 N·m。两次均没有实测到 15 N·m。固件 `rl_traj_fdr.torque_limit` 和 deploy 的 `recovery_config.json` 都把手臂项设为 14。该值用于把手臂位置比例项限制在约 ±14 N·m 的范围，并非额外的 1 N·m 差异。

两次 `/joint_ctrl` 的前馈 `tau` 无法直接互比：固件内部命令未公开；deploy 已发送消息中各关节 `tau=0`，实际由目标角、`kp/kd` 和下游电机控制产生力矩。将 deploy 已发送 PD 项 `kp(q_target-q)-kd*dq` 与 `tau_est` 对照，在动作至故障前的手臂关节上相关系数约 0.95～0.97。这支持外部目标进入了执行链并产生对应受力，但不能证明固件最终电机目标与 `/joint_ctrl` 完全相同。`tau_est` 也不是电流传感器直接测出的轴输出力矩。

固件试验动作期间 1 Hz 电池日志的最小电压 50.6 V、最大放电采样 -10.6 A；deploy 对应为 39.9 V、-63.3 A（15:36:29.871，故障前）。这与 deploy 承受更高负载一致。电压下降也可能进一步降低可用输出；因采样仅约 1 Hz，无法证明它是最先触发停滞的原因。deploy 没有低电量拒绝切换模式的日志。

deploy 故障前 15:36:23.718 已有一次右臂 CAN8 读取失败，15:36:30.103 起出现连续 CAN8 失败，15:36:30.127 关节 9 报堵转，15:36:30.163 关节 2 报堵转。固件成功试验在 15:26:07.338 也出现过一次 CAN8 读取失败，因此单次 CAN8 告警不足以解释为什么仅 deploy 失败。故障后关节 2/9 的反馈出现零值，不能当作真实关节瞬间归零，也不应纳入正常跟踪误差统计。

## 原因判断与下一步

**可直接证明的失效机制**：deploy 在双臂未完成回收时继续推进髋部起身目标，双臂持续接近力矩上限而几乎不动，髋部同时产生更大力矩与电流负载，最终双臂堵转并退出 Custom。策略代码按固定 0.02 s 推进轨迹，不以手臂已到位作为进入下一帧的条件，这会放大先发生的手臂跟踪失败。

**仍未唯一确定的首因**：两次试验起始手臂关节差约 0.4～0.8 rad，接触状态未知；同时固件内部参考、Custom 处理后的最终电机目标、足底/手臂接触力和高频电流没有公开。现有数据无法区分初始支撑几何、策略观测/相位差、Custom 下游执行差异或供电压降各自的贡献。仿真成功不能消除这些实机差异。

下次对照先按厂家流程确认并清除关节 2/9 故障与持续通信告警，再让两次试验的初始 22 关节角、机身姿态和支撑方式尽量一致，同时保留原始 policy 参考、发布后目标、关节反馈、IMU 与侧面视频。不要提高力矩上限或关闭堵转保护来验证假设。
