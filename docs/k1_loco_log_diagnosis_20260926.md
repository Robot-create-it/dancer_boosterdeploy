## 能解释两种输入均在 X 方向异常的候选原因

### 1. base 模型的实机配置与配套配置不一致

`tasks/locomotion/nested_locomotion.py:69` 的路由规则表明：纯 X 前进/后退使用 base，纯旋转超过阈值使用 turn。两者是不同 ONNX；旋转正常不能证明 base 闭环正常。纯 X 变化本身始终走 base，不应先假定是模型频繁切换。

`tasks/locomotion/robots/k1/loco.py:27` 用 K1 walk 的 PD 覆盖实机参数：

| 关节组 | loco JSON | 实机生效 |
|---|---|---|
| 髋、膝 Kp/Kd | 100/2 | 100/2 |
| 踝 pitch、roll Kp/Kd | 50/1 | **65/1** |

踝部刚度提高 30%，阻尼保持不变。前后移动涉及矢状面关节跟踪，这个差异应优先做单变量验证；它是已确认的配置差异，不是已经测得的振荡根因。

实机覆盖在 Portal 构造时应用，**只修改 loco_config.json 的 kp_22 并不会改掉这组实机覆盖**。

### 2. X 方向重力观测偏移被移除

配套 JSON 和本机源仓库 `dancer-robocupdemo/src/sim_adapter/sim/src/policy/loco_policy.cpp::buildFrame()` 使用 `[0.015, 0, 0]` 重力偏移。当前 Python 已删除这一加法；`git diff` 可直接看到删除。

该差异持续影响模型输入，与前后倾姿态相关，可能在 base 上比 turn 更明显。如果稳定保持很小的 X 命令仍持续抖动，应与 PD 一起优先验证。没有闭环对照，不能声称 0.015 偏移必然是主因。

### 3. 速度斜坡被移除，输入跳变直接进入模型

源实现每 20 ms 对 X 命令限制增量 `+0.026 / -0.032 m/s`；当前 `LocoCommandProcessor.process()` 直接使用输入，只保留幅值和耦合限制。

离线实测：从零按一次 w，模型命令立即变为 `[0.15, 0, 0]`；空格立即归零。相对于原先单帧正向增量，首次跳变约为 5.77 倍。遥控器突推同样会跳变。

它特别能解释起步、停步、变速时的抖动；若恒定命令长期抖动，仅恢复斜坡不一定解决。`action_filter=0.8` 是 80% 新目标、20% 旧目标，也不能等价替代命令斜坡。

### 4. 键盘和遥控器话题没有输入来源仲裁

`booster_deploy/utils/remote_control_service.py:198` 每次话题回调无条件重写 vx/vy/vyaw，而键盘直接修改同一组变量。

提取原函数进行无 ROS 离线复现：

```text
按 w：vx = 0.1（归一化）
收到居中遥控器消息：vx = -0.0
```

如果键盘测试时 ROS fallback 活跃且遥控器持续发消息，命令会被清零或覆盖，可能反复启停。这个覆盖行为已证实，本次运行是否发生尚无逐帧记录；而且它也会覆盖 yaw，不能据此独立解释方向差异。

执行 `.venv/bin/python -m unittest discover -s tests -q`：17 项，15 项通过、2 项跳过，无失败。这说明当前映射、模型调用和离线控制流程的回归检查通过，不证明硬件稳定。另离线确认了路由、实际 PD、单次键盘命令和话题覆盖行为。

建议下一次对照先让输入来源唯一，并记录每周期的：单调时间、输入来源、原始/处理后命令、路由、状态时间戳、推理耗时、IMU、关节 q/dq/tau、原始动作、目标位置、实际发布 Kp/Kd。这样能判断“目标先抖”还是“目标正常而实际关节抖”。仅用 tee 保存现有终端输出仍缺少这些关键数据。

随后逐项验证：踝 Kp 65→配套配置 50（Kd 暂不变）；恢复重力偏移；恢复原命令斜坡。每次只改一项，在受控支撑条件下从小速度对照，并在明显抖动时结束该次测试。遥控器原生任务冲突另行隔离；不要将 turn 强行用于直行作为修复。
